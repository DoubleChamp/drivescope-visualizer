# DriveScope 개발 로드맵

DriveScope는 카메라, LiDAR, 객체 인식 결과와 예상 주행 경로를 하나의 시간축에서 동기화해 자율주행 문제 장면을 분석하는 학습 프로젝트다.

## 진행 원칙

- 한 번에 아래 항목 하나만 진행한다.
- 구현 전에 무엇을 만들고 왜 필요한지 설명하고 사용자의 승인을 받는다.
- 각 항목이 끝나면 직접 실행해 결과를 확인하고 `docs/PROGRESS.md`를 갱신한다.
- 사용자가 핵심 원리를 설명할 수 있는지 확인한 뒤 다음 항목으로 넘어간다.
- 실제 데이터보다 가상 데이터로 뷰어와 동기화 구조를 먼저 완성한다.
- 앞으로는 별도 작업 브랜치를 만들지 않고 `main`에서만 작업한다.
- 승인된 한 단계의 구현, 검증과 문서 갱신이 끝나면 `main`에 commit까지만 한다. `origin` push는 사용자가 GitHub Desktop에서 직접 수행한다.

## 현재 상태

- **Phase 0 — 완료:** 개발 도구 준비, Next.js 초기화, Three.js 설치, 실행 검증과 로컬 프로젝트 문서 구성을 마쳤다.
- Git 작업은 현재 GitHub Desktop의 내장 Git으로 충분하다. 별도의 Git for Windows 설치와 시스템 PATH 등록은 필요해질 때 진행할 수 있다.
- **Phase 1 — 완료:** `feat/phase-1-three-scene` 브랜치에서 Client Component 경계, React가 소유하는 Canvas, Three.js Scene, PerspectiveCamera, WebGLRenderer, GridHelper, 창 resize 처리, `requestAnimationFrame` 렌더 루프와 전체 cleanup을 구현하고 검증했다.
- **Phase 2 — 완료:** 가상 포인트 10,000개의 Buffer 구조와 Material 조정, 포인트 수와 rAF 기반 FPS 표시를 구현했다. 포인트 100개와 10,000개를 각각 측정하고 FPS 계산과 React·Three.js 책임 분리를 확인했다.
- **다음 단계:** Phase 3의 첫 항목으로 모든 Frame에 공통으로 사용할 timestamp 단위와 기준 시점을 결정한다.

## Phase 1: 가장 작은 Three.js 장면

상태: **완료**

1. Client Component가 필요한 이유와 브라우저 전용 API의 관계를 학습한다.
2. React가 소유할 빈 `<canvas>` 요소를 만든다.
3. Three.js `Scene`을 만든다.
4. `PerspectiveCamera`를 만들고 위치와 시야를 설정한다.
5. `WebGLRenderer`를 Canvas에 연결한다.
6. 공간의 기준을 볼 수 있도록 `GridHelper`를 추가한다.
7. 창 크기 변경에 맞춰 Camera와 Renderer 크기를 갱신한다.
8. `requestAnimationFrame` 렌더 루프를 시작하고 중지하는 흐름을 만든다.
9. 컴포넌트 해제 시 이벤트, 애니메이션 프레임과 Three.js 리소스를 정리한다.

완료 조건:

- 브라우저에서 Grid가 보이고 창 크기를 바꿔도 올바르게 표시된다.
- 개발 중 불필요한 중복 렌더 루프나 리소스 누수가 발생하지 않는다.
- 사용자가 Canvas, Scene, Camera, Renderer, Grid와 렌더 루프의 역할을 설명할 수 있다.
- 사용자가 React의 생명주기와 Three.js 렌더링 책임이 어떻게 나뉘는지 설명할 수 있다.

## Phase 3: Frame 데이터 모델

상태: **대기**

1. 모든 데이터에 공통으로 사용할 timestamp 단위와 기준 시점을 결정한다.
2. LiDAR Frame 타입을 정의한다.
3. Camera Frame 타입을 정의한다.
4. Object Detection 타입을 정의한다.
5. Trajectory 타입을 정의한다.
6. Vehicle State 타입을 정의한다.
7. Event 타입을 정의한다.
8. 0초부터 급제동 이후까지의 가상 문제 장면 데이터를 만든다.

완료 조건:

- 사용자가 센서별 데이터 주기가 다른 이유를 설명할 수 있다.
- 사용자가 특정 재생 시간에 사용할 센서 Frame을 선택하는 기준을 설명할 수 있다.
- 렌더링 코드와 Frame 데이터 모델이 서로 독립된 책임으로 유지된다.

## Phase 4: 재생과 시간 동기화

상태: **대기**

1. 현재 재생 시간을 나타내는 상태를 만든다.
2. 재생과 정지 동작을 추가한다.
3. 타임라인 드래그로 원하는 시점에 이동하게 한다.
4. 현재 시간에서 가장 가까운 Frame을 찾는 함수를 만든다.
5. 서로 다른 주기의 센서 Frame을 timestamp 기준으로 동기화한다.
6. 타임라인에 급제동 이벤트 마커를 표시한다.
7. seek 직후 모든 센서 장면이 같은 시간 기준으로 갱신되게 한다.

완료 조건:

- 재생, 정지와 타임라인 이동이 예측 가능한 하나의 재생 시간 상태를 사용한다.
- 타임라인을 이동한 뒤 카메라, LiDAR와 Annotation이 올바른 Frame으로 갱신된다.
- 급제동 이벤트 위치가 시나리오의 timestamp와 일치한다.
- 사용자가 센서별 최근접 Frame 선택 규칙과 동기화 오차의 의미를 설명할 수 있다.

상태: **대기**

1. 보행자 3D 바운딩 박스를 표시한다.
2. 차량 3D 바운딩 박스를 표시한다.
3. 예상 주행 경로를 표시한다.
4. 경로와 보행자의 충돌 예상 구간을 강조한다.
5. 장면에서 보행자를 선택할 수 있게 한다.
6. 선택한 객체의 기본 정보를 표시한다.
7. 같은 시간축의 전방 카메라 이미지 패널 1개를 연결한다.

완료 조건:

- 핵심 데모의 보행자 등장, 인식, 충돌 예상과 급제동 흐름을 한 타임라인에서 확인할 수 있다.
- 객체를 선택하면 해당 객체의 기본 정보가 정확히 표시된다.
- 카메라 패널과 3D 장면이 같은 재생 시점을 나타낸다.
- 사용자가 화면 UI는 React, 3D 객체와 선택 처리는 Three.js가 맡는 이유를 설명할 수 있다.

## Phase 6: 로딩과 성능

상태: **대기**

1. 현재 Frame을 재사용할 수 있는 캐시를 만든다.
2. 이전·다음 Frame을 미리 가져온다.
3. 캐시 크기 제한과 제거 규칙을 정한다.
4. 포인트 위치 Buffer를 Frame마다 새로 만들지 않고 재사용한다.
5. Geometry, Material, Texture와 Renderer의 정리 시점을 검증한다.
6. FPS를 측정하고 표시한다.
7. Frame 로딩 시간을 측정하고 표시한다.
8. 측정 결과 병목이 데이터 파싱임을 보여줄 때만 Worker를 도입한다.

완료 조건:

- 타임라인 이동 시 캐시와 prefetch의 적중 여부를 확인할 수 있다.
- 캐시가 설정한 크기를 넘지 않고 장시간 재생 후에도 메모리가 계속 증가하지 않는다.
- Buffer 재사용 전후의 FPS, 로딩 시간 또는 할당량 차이가 수치로 기록된다.
- Worker 도입 여부가 추측이 아니라 측정 결과를 근거로 결정된다.

## Phase 7: 실제 데이터와 결과물

상태: **대기**

1. Python으로 nuScenes mini를 DriveScope Frame 형식으로 변환한다.
2. 실제 LiDAR와 전방 카메라 데이터를 뷰어에 연결한다.
3. 누락 파일, 잘못된 timestamp와 로딩 실패를 처리한다.
4. 가상 데이터와 실제 데이터의 성능을 같은 기준으로 비교한다.
5. 설치, 실행, 사용법과 데모 설명을 `README.md`에 정리한다.
6. 최종 데이터 흐름과 책임 분리를 아키텍처 문서에 반영한다.
7. 웹에서 실행할 수 있도록 배포한다.
8. 핵심 문제 장면을 보여주는 1분 데모 영상을 만든다.

완료 조건:

- nuScenes mini의 카메라와 LiDAR 데이터가 같은 타임라인에서 재생된다.
- 데이터 오류가 사용자에게 이해 가능한 상태로 표시되고 앱이 복구 불가능하게 중단되지 않는다.
- 실제 데이터의 포인트 수, FPS와 Frame 로딩 시간이 기록되어 가상 데이터 결과와 비교된다.
- 새 사용자가 README만으로 설치하고 핵심 데모를 재현할 수 있다.
- 배포된 결과물과 1분 데모 영상으로 DriveScope의 분석 목적과 기술적 선택을 설명할 수 있다.
