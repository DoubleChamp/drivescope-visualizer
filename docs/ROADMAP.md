# DriveScope 개발 로드맵

DriveScope는 카메라, LiDAR, 객체 인식 결과와 예상 주행 경로를 하나의 시간축에서 동기화해 자율주행 문제 장면을 분석하는 학습 프로젝트다.

## 진행 원칙

- 한 번에 아래 항목 하나만 진행한다.
- 구현 전에 무엇을 만들고 왜 필요한지 설명하고 사용자의 승인을 받는다.
- 각 항목이 끝나면 직접 실행해 결과를 확인하고 `docs/PROGRESS.md`를 갱신한다.
- 사용자가 핵심 원리를 설명할 수 있는지 확인한 뒤 다음 항목으로 넘어간다.
- 실제 데이터보다 가상 데이터로 뷰어와 동기화 구조를 먼저 완성한다.
- 앞으로는 별도 작업 브랜치를 만들지 않고 `main`에서만 작업한다.
- 승인된 한 단계의 구현, 검증과 문서 갱신이 끝나면 `main`에 commit까지만 한다. `origin` push는 사용자가 GitHub Desktop에서 직접 수행한다.

## 현재 상태

- **Phase 0 — 완료:** 개발 도구 준비, Next.js 초기화, Three.js 설치, 실행 검증과 로컬 프로젝트 문서 구성을 마쳤다.
- Git 작업은 현재 GitHub Desktop의 내장 Git으로 충분하다. 별도의 Git for Windows 설치와 시스템 PATH 등록은 필요해질 때 진행할 수 있다.
- **Phase 1 — 완료:** `feat/phase-1-three-scene` 브랜치에서 Client Component 경계, React가 소유하는 Canvas, Three.js Scene, PerspectiveCamera, WebGLRenderer, GridHelper, 창 resize 처리, `requestAnimationFrame` 렌더 루프와 전체 cleanup을 구현하고 검증했다.
- **Phase 2 — 완료:** 가상 포인트 10,000개의 Buffer 구조와 Material 조정, 포인트 수와 rAF 기반 FPS 표시를 구현했다. 포인트 100개와 10,000개를 각각 측정하고 FPS 계산과 React·Three.js 책임 분리를 확인했다.
- **Phase 3 — 완료:** 공통 timestamp 기준, 모든 Frame·Event 타입과 0~15초의 가상 급제동 시나리오 데이터를 정의하고 검증했다.
- **Phase 4 — 완료:** 현재 재생 시간 state, 재생·정지, 타임라인 드래그, Frame 선택·센서 동기화와 급제동 이벤트 마커를 추가하고 선택된 Camera·LiDAR·Object Detection Frame을 화면에 반영했다.
- **Phase 5 — 기능 구현과 구조 정리 완료, 이해 확인 대기:** 보행자·차량 박스, 예상 경로와 충돌 구간, 객체 선택·기본 정보와 같은 시간축의 가상 전방 카메라 패널을 구현했다. 이어서 Viewer를 재생·선택·Three.js 런타임 Hook과 표시 컴포넌트로 책임별 분리했다.
- **Phase 6 — 기능 구현 완료, Frame 로딩 시간 이해 확인 대기:** LiDAR Frame의 CPU 캐시·prefetch·최대 5개 LRU 축출과 모의 로더 실행 시간 표시를 연결했다. 현재 측정에서는 Worker를 도입할 병목이 확인되지 않았다.
- **Phase 7 — 결과물 구현·검증 완료, 원리 이해 확인 대기:** 실제 센서 연결·좌우 방향·이미지 버퍼와 오류 안내·재시도를 구현했다. 성능 기준선·README·아키텍처를 정리하고 Public Blob 자산 업로드와 공개 Viewer의 실제 재생·복구·모바일 검증을 마쳤다. 실제/가상 선택 UI와 전환 초기화, 60초 자막 영상 촬영·편집을 완료했다. 데이터 처리·성능 측정을 강조하는 포트폴리오 홈과 사이트 내 영상 재생도 구현하고 로컬 production 브라우저에서 검증했다. 새 소개 페이지의 공개 반영은 사용자 push 뒤 확인한다.
- **Viewer UI — 마감과 후속 정리 검증 완료:** 실제 모드의 차량 위치·소스 상태·빈 상태를 반영했다. 정상 이미지 교체 안내는 숨기고 500ms 지연만 헤더에 표시하며, 제목·요약과 3D 표시 컴포넌트를 분리했다. 모바일·객체 선택·기존 센서·캐시·오류 복구 동작도 회귀 검사했다.
- **홈·영상 가독성 — 수정 완료:** 밝은 배경·본문 대비·세로 최적화 설명·넓은 영상으로 홈을 정리했다. 60초 MP4 자막은 크게·굵게·위로 배치하고 모바일 네이티브 컨트롤 여백을 확보했다. 검증 범위와 마감 상태는 PROGRESS를 따른다.
- **로더 구간 측정 — 구현·검증 완료:** 실제 LiDAR의 응답 헤더·본문 읽기·좌표 준비를 나누고 현재 요청과 prefetch의 최초 시작 주체를 기록한다. cache hit는 새 측정이 없으며, 공유된 Promise는 최초 시작의 종류·시간을 유지한다. 기존 전체 로딩 지표와 13.9ms 기준선은 유지한다.
- **Frame 표시 안정성 — 수정·점검 완료:** 동기화 행의 두 줄 공간·숫자 줄바꿈을 고정하고, 다음 LiDAR 준비 중 마지막 점군을 유지한다. production 재생·320~2236px·지연·오류·재시도·모드 전환을 검증했다. 카메라 2슬롯의 사진 역행·빈 사진은 검사 표본에서 없었다. 점군·사진의 keyframe 간격은 그대로다.
- **3D 시점 이동 — 구현·검증 완료:** 실제 재생 중 Camera 위치·주시점의 경과 시간 기반 추종을 추가했다. 정지·seek·최초 표시는 기록된 목표로 즉시 맞춘다. Camera 이동 전후·60/75Hz 일치·소스 전환과 기존 표시 안정성을 검증했다. 센서·ego pose·JPEG 보간은 이번 범위 밖이다.
- **P.S. 1~6 — 구현·비교 완료:** 계측·Worker 유지 판단·cursor/이진 탐색·sweeps 비교를 마쳤다. 이어 사용자 승인으로 로컬 Viewer에 개별 sweep과 실제 50ms 갱신을 적용했다. 누적은 비교용이며 공개 데이터는 별도 교체 전까지 keyframe이다. [측정과 판단](./PERFORMANCE.md)
- **홈 진입 분리 — 구현·검증 완료:** 이전 어두운 카드 홈(`/`)을 복원하고 뷰어 열기(`/viewer`)와 프로젝트 개요(`/project`) 버튼을 나눴다. 기존 소개·영상·Frame 선택 예시는 `/project`로 옮겼으며 모바일·키보드·실제 Viewer 왕복을 확인했다. 공개 반영은 사용자 push 뒤 확인한다.
- **프로젝트 설명 가독성 — 수정·검증 완료:** Viewer 진입 문구 통일·코드 펼치기/파일별 코드 링크 제거·쉬운 설명·본문 크기/줄 간격/대비·단계별 흐름·문제 해결 카드·모바일 측정 표를 정리했다. 기존 영상·Frame 선택 예시·Viewer 왕복은 검증했으며 Worker 선택 UI는 보류한다.
- **공개 링크·용어 정리 — 수정·검증 완료:** GitHub 저장소·문서 링크 6개를 공개 소개에서 제거하고 홈·소개·접근성 이름을 Viewer 영어 표기로 통일했다. production build·모바일·영상·실제/가상 Viewer 왕복을 검증했다. 공개 반영은 사용자 push 뒤 진행한다.
- **소개 UI 간결화·링크 복원 — 수정·검증 완료:** 사용자 요청으로 GitHub 링크 6개를 복원하고 소개를 흰 배경·큰 제목·넓은 실제 화면·여백으로 정리했다. 반복되는 장식·숫자 요약·카드 테두리를 줄였다. production 브라우저와 localhost:3000·모바일·영상·Viewer 왕복을 확인했다. 공개 반영은 사용자 push 뒤 진행한다.
- **다음 단계:** 실제 50ms 재생과 센서 timestamp, Camera smoothing과 기록 보간, 누적 잔상의 차이를 설명하고 이해를 확인한다. 앞선 Worker/cursor의 이해 확인도 남아 있다. 사용자 push와 새 Vercel build 뒤 공개 반영을 확인하며 공개 sweep 업로드/URL 교체는 별도로 정한다. scene 목록·다중 카메라와 방화벽은 현재 구현 범위 밖이다.

## Phase 1: 가장 작은 Three.js 장면

상태: **완료**

1. Client Component가 필요한 이유와 브라우저 전용 API의 관계를 학습한다.

### 실제 데이터 확장 검토 의견 (미구현)

사용자가 짧은 실제 로그와 다른 데이터 목록·다중 카메라의 필요성을 물어 검토했다. 현재 scene은 19.185초이며 nuScenes는 원래 약 20초 scene 단위로 구성된다. mini에는 scene 10개가 있으므로 다른 장면을 고를 여지가 있다. [공식 nuScenes 튜토리얼](https://www.nuscenes.org/tutorials/nuscenes_tutorial.html)

추천 순서는 **서로 다른 상황의 scene 3~5개와 선택 목록 → 카메라 채널 선택 → 필요할 때 동시 다중 카메라 표시**다. 이 의견은 후속 구현 승인이 아니다.

- scene 목록에는 이름·설명·길이·manifest URL을 두고 선택한 scene의 센서만 가져온다. 기존 변환기의 `--scene-index`를 사용할 수 있다. scene 전환 시 이전 시계·선택·캐시·Three.js 세션을 정리해야 하며, 서로 다른 장면을 한 연속 주행처럼 붙이지 않는다.
- nuScenes의 카메라 6개는 같은 장면의 여러 방향을 제공한다. 카메라를 추가해도 로그 길이는 늘지 않는다. 현재 v3 manifest는 `CAM_FRONT` 하나로 고정돼 있으므로 채널별 Frame·선택·로딩·이미지 버퍼를 표현하는 계약 변경이 필요하다. 먼저 한 패널에서 채널을 선택하는 방식이 적절하다. [공식 센서 구성](https://www.nuscenes.org/)
- 중간 sweeps는 현재 scene 안의 시간 해상도를 높이는 후보다. 더 긴 연속 주행이 꼭 필요하면 장시간 로그를 제공하는 별도 데이터 소스와 변환기를 검토한다.
